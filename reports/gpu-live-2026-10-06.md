# Live GPU session, 2026-10-06

One rented GPU, one session, one run per configuration. Every number below is read from the artifacts in
`reports/gpu-live-2026-10-06/`; nothing is estimated or filled in. Where something was not measured it says so.

## What was run

| | |
|---|---|
| Engine / version | vLLM 0.30.0 (image digest in `deployment.json`) |
| Model | Qwen/Qwen2.5-7B-Instruct, float16, no weight quantization, `max_model_len` 16384 |
| GPU | 1 x NVIDIA L40S (46068 MiB), RunPod secure cloud, US-MO-1 |
| Price | 1.09 USD/hour (quoted before renting) |
| Workload | held-out replay workload (`data/heldout-quality-workload.json`), 100 requests per cell |
| Benchmark client | a laptop, reaching the pod through an SSH tunnel (about 270 ms round trip) |
| Pod lifetime | 16:26:41Z to 17:41:57Z, 75.3 minutes, then terminated and confirmed gone |

(`application_revision`, `application_config_sha256`, quantization fields).

**Limits that apply to everything below:** single run per configuration, single GPU, one host, and a client that was
remote from the server. Latency includes the tunnel. Differences smaller than the run-to-run spread are not findings.

What this supports:

- Throughput rises about 8x from concurrency 1 to 32 (0.215 to 1.725 req/s) and is flat or slightly lower at 64
  (1.608). At 64 the two repeats were 1.541 and 1.675, so 32 versus 64 is inside the run-to-run spread.
- The flattening at 64 is not KV-cache exhaustion: peak KV usage was 42% and there were no preemptions. The engine
  queue did build (mean 8.4 to 8.9 waiting, peak 49 to 57), so requests were queueing, not being evicted.
- GPU utilization is already about 100% at concurrency 4, while throughput still rises 2.4x from there to 32.
  Utilization saturating does not mean the GPU has no headroom, and it is not a measure of efficiency. It says only
  that a kernel was running almost all the time.
- This run was 17 to 27% slower than the earlier FP16 run at every level. The cause was not established. The host,
  day and network path differed. It was not investigated further, and no explanation is offered here.

## 2. Failure-behaviour test, SIGSTOP / SIGCONT (main fault)

Fault: `kill -STOP` on the vLLM API server process only, then `kill -CONT`, issued over SSH, while 16 concurrent
requests were in flight and the GPU sampler ran. Run after the clean sweep. No hosted fallback exists, and none was
added; "fallback observed" below means only what the benchmark saw.

Timeline (seconds from load start): inject issued 60.0, returned 61.5; restore issued
120.0, returned 121.6.

| window (by when the request was sent) | offered | ok | error rate | status counts |
|---|---|---|---|---|
| before | 115 | 115 | 0.0% | {'ok': 115} |
| injection_transition | 19 | 3 | 84.2% | {'ok': 3, 'timeout': 16} |
| during | 29 | 8 | 72.4% | {'timeout': 21, 'ok': 8} |
| after | 183 | 182 | 0.5% | {'ok': 182, 'timeout': 1} |

- Time to first error: 3.3 s. Time to recovery (first ok request sent after restore): 6.8 s
  from restore issued.
- 16 requests sent during the stall completed only after the restore; 8 of them were ok. They are counted as errors or
  successes by when they were sent, not by when they finished.
- `/health/serving` reported unhealthy 4.6 s after the inject and healthy
  2.2 s after the restore, which matches the documented behaviour.
- The injection-transition window (requests in flight when the fault was issued) is reported separately so the
  inject command's own latency does not pollute the "during" window.

GPU by phase (offset-corrected samples; see `failure-behaviour/gpu-by-phase.txt`). Columns: phase, samples, mean
util %, min util, max util, mean power W.

```

stall, first 15 s after inject returned      15   60.0     0   100      227

stall, rest (30 s to restore)                28    0.0     0     0      119
```

GPU utilization fell to 0% after the engine's in-flight work finished (the engine process kept running while the API
server was stopped) and returned to about 100% after the restore.

## 3. Failure-behaviour test, hard kill and restart

Fault: `kill -9` of the whole vLLM process group, then restart of the server with the same flags. Concurrency 16.
**Recovery time includes model load**, because the server was restarted from scratch, so it is not comparable with the
SIGSTOP recovery time.

Timeline: kill issued 60.0, returned 61.7; restart command issued 90.0, returned
91.7.

| window | offered | ok | error rate | status counts |
|---|---|---|---|---|
| before | 119 | 119 | 0.0% | {'ok': 119} |
| injection_transition | 17 | 1 | 94.1% | {'ok': 1, 'error': 16} |
| during | 1695 | 0 | 100.0% | {'error': 1695} |
| after | 3926 | 355 | 91.0% | {'error': 3568, 'ok': 355, 'timeout': 3} |

- Time to first error 1.7 s. Time to recovery, **includes model load**: 64.5 s from restore issued
  (62.8 s from restore returned). Health recovered 62.2 s after the restore, matching the documented
  behaviour.
- The "after" window (sent after the restart command returned) has a 91% error rate because the model was still
  loading for the first minute of it. Grouped by when requests were sent relative to recovery:

```
  restore issued -> first success sent after it (model loading)  sent= 3584 ok=  16 error_rate=0.996  [90.0s .. 154.5s]
  after recovery (first success to end of load)                  sent=  342 ok= 339 error_rate=0.009  [154.5s .. 378.1s]
  errors sent after recovery: 3 {'TimeoutError'}
```

- After recovery 339 of 342 requests were ok; the 3 errors were client timeouts.
- No request succeeded while the fault was active. 0 of the 16 requests sent during the outage finished ok after the
  restore.

## 4. Prefix caching on versus off

Two runs of the same workload in cache mode `reuse` (prefixes preserved), concurrency 4 and 16, two repeats each, with
only `--enable-prefix-caching` / `--no-enable-prefix-caching` different between them; the manifests differ only in
`run_id` and `prefix_caching`. The server was restarted between arms.

| concurrency | hit rate (on) | hit rate (off) | req/s on | req/s off | change | p95 s on | p95 s off | change | GPU util on / off |
|---|---|---|---|---|---|---|---|---|---|
| 4 | 86.3% (ok) | unavailable: no prefix-cache queries during the cell | 0.830 | 0.746 | -10% | 13.3 | 13.9 | +5% | 100% / 99% |
| 16 | 99.7% (ok) | unavailable: no prefix-cache queries during the cell | 2.964 | 1.447 | -51% | 11.5 | 24.2 | +111% | 98% / 99% |

- With caching on, the engine reported a hit rate of 86% at c=4 (the first repeat was lower, 72.8%, while the cache
  warmed) and 99.7% at c=16.
- With caching off, vLLM 0.30.0 reported no prefix-cache queries at all, so the hit rate is shown as unavailable,
  not as 0%.
- At c=16, caching off was 51% lower in throughput and 111% higher in p95 latency. At c=4 the difference (10% lower
  throughput, 5% higher p95) is about the size of the gap between the two caching-on repeats (0.791 versus 0.868
  req/s), so it is not claimed as an effect.
- Because the workload reuses long shared prefixes, this is the favourable case for prefix caching. It says nothing
  about workloads without shared prefixes (the clean sweep, in `bust` mode, is that case).
- GPU utilization was about 100% in both arms and does not distinguish them.

## 5. Serial versus concurrent

The legacy harness at the same batch size, with and without `--serial`, on a fixed prompt set.

| batch size | serial wall s | concurrent wall s | wall speedup | throughput ratio | output tokens serial / concurrent | length caveat |
|---|---|---|---|---|---|---|
| 4 | 16.6 | 8.7 | 1.91x | 2.89x | 590 / 892 | yes: total output length differs between the runs by more than 10... |
| 16 | 91.3 | 16.8 | 5.44x | 5.43x | 2921 / 2918 | no |

- At batch size 16 the two runs produced the same total output (2921 versus 2918 tokens), so the 5.4x speedup is a
  like-for-like comparison of one request at a time against 16 at once.
- At batch size 4 the total output length differed by more than 10% (590 versus 892), so that ratio mixes batching
  with output length and is shown only with its caveat.
- This is direct evidence for continuous batching on this server, one run per arm.

## What this evidence does not support

- Any claim about other GPUs, other models, quantized weights, or multi-GPU serving.
- Any claim that results hold across repeated sessions: each configuration ran once (the sweep and prefix arms had two
  repeats in the same session, which is not independence).
- The cause of the slowdown against the earlier FP16 run.
- That GPU utilization measures efficiency or headroom.
- Hard-kill recovery as a production recovery time: it includes model load from local disk on this host.
- Any local-to-hosted fallback behaviour, because none exists.
- SGLang or any other engine: the engine option exists, but only vLLM was run.
- Quality of answers under any configuration here; this session measured speed and failure behaviour only.
